# 连续工具跳数诊断

本次保留诊断，并增加运行时系统规则及客户端限额提示来源标记。
不调整 8 跳/连续 3 跳错误阈值，不改变计数、重置、重试或请求调度。

## 现场日志结论及针对性调整

用户提供的现场日志中，15:25 的新轮次实际只有 1 跳，随后模型自行输出了 8 跳提示；
当时没有客户端限额事件。整份日志的客户端限额事件只有更早的 14:38 一次。
因此本次针对模型误报处理，不将下述静态风险直接认定为本次根因。

`ToolHopPolicy` 在每次请求组装系统提示时追加固定规则，覆盖自定义提示和无工具场景，
不写入 SystemPromptManager，也不覆盖用户保存的提示词。正常和历史组装失败的回退请求
共用这一组装入口。规则明确旧版无来源标记的提示也仅代表当时轮次。

程序实际触发跳数或错误上限时，界面和历史使用同一份带
`【客户端工具调用限制】` 标记及历史时效说明的提示。消息仍保持 assistant 角色，
不删除旧历史，不以提示词替代程序安全限制。提示词改善仍需手机复现观察，不保证模型永不误报。

## 静态调查发现

- `sendMessageToSister` 在有效用户消息入口清零；正常模型回复完成时也清零。
- 工具调用前的说明文字仍属于工具回复，不是独立结束的纯文字回复。
- `sendChatRequest`（输入法发送及广播入口调用）启动新 usage turn，但不调用计数重置。
- 跳数是 Activity 共享字段，不按 usage turn 隔离；旧轮次成功响应和工具结果没有在计数处理处拒绝。
- 工具 finish 在响应回调中递增，重置和工具结果判断通常在 UI 线程；存在并发和旧回调影响新轮次的可能。
- 限额提示作为 assistant 写入历史，模型可能复述；没有现场日志，不能判定截图是否确实触发本地限额。

## 收集方法

安装包含诊断的版本，复现后提取 `[TOOL_HOP_DIAG]` 行，保留从新消息发送前到停止提示后的完整时间段。
日志优先位于 `/sdcard/Download/sisterfuture_logs/`，不可写时位于应用私有 files/sisterfuture_logs。
新增行只记录事件、Activity 标识、轮次、消息 ID、计数、线程及文本长度/提示特征布尔值，
不记录消息正文、工具参数、结果或凭据。既有其他日志仍可能含敏感内容，请勿直接公开整份日志。

## 判断方法

- `reset_before` / `reset_after`：重置原因及前后计数，`new_turn_after`：新轮次开始时的计数。
- `alternate_send_entry` 后新轮次仍带旧 hop：验证另一发送入口未重置的问题。
- `request_bound`：将 requestId、消息 ID 与轮次对应，便于识别同一响应重复结束事件。
- `model_tool_finish_before_increment` / `after_increment`：一次工具回复结束导致一次递增。
- `tool_results_guard_check`：实际限额判断时计数；`staleTurn=true` 表示来源轮次不是当前轮次。
- `app_generated_limit_message`：程序确实生成了限额提示，附对应消息 ID。
- `model_text_finish` 且 `mentionsHopLimit=true`：模型输出包含类似限额措辞，需与同时间段的程序限额事件对照。
  该布尔标记只是启发式特征，不能单独判定模型复述或错误。

如日志缺失或截断，不能凭缺少某事件排除对应路径。诊断快照不加锁，不用于修复或保证并发一致性。
